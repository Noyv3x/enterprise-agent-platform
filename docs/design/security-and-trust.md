# Security and trust

## Execution boundary

The sandbox is the tenant execution boundary. Pi is not a sandbox. Runtime never runs tenant shell commands locally and never discovers host context, skills or extensions. Only host Manager owns Docker and executes audited sandbox operations. There is no host-execution product tool, approval workflow or approval-based escape hatch.

Personal AI and each channel have distinct workspaces/sandboxes. Chat uses one network-disabled sandbox per user, shared across that user's conversations. Chat file tools restrict paths to the active conversation directory; bash only sets cwd and can reach the same user's other chat files. Do not describe conversation directories as separate security boundaries.

Use Manager's `agent` and `chat` resource profiles; identities bind a sandbox to its workspace and profile at creation. Resource limits are in [deployment](../operations/deployment.md). No business container or sandbox receives the Docker socket.

## Authentication and authorization

- Platform authenticates signed cookies and checks active users and `token_version` on requests. Password/revocation changes invalidate prior tokens.
- Administrators can impersonate any other active account (管理员代入). This simply issues a normal session for the target and replaces the caller's cookie, as if the target had just signed in: no flag marks the session as impersonated, other sessions and `token_version` are unchanged, and returning to the admin requires signing in again.
- Cookie-authenticated mutations and login must be same-origin: the `Origin` must equal the configured public base URL or the origin the browser actually used. With `AGENT_PLATFORM_TRUSTED_PROXY=1` (container deployments, where the Manager gateway discards client-supplied forwarding headers and rebuilds them from the accepted connection), that request origin comes from `X-Forwarded-Proto`/`X-Forwarded-Host` and login throttling keys on `X-Forwarded-For`; otherwise `Host`, the public scheme and the TCP peer are used.
- Server-side ownership protects personal scopes, chat conversations, files, schedules and browser takeover. Channel read/manage permissions come from permission groups; there is no implicit membership policy.
- Runtime bearer, internal tool bearer, Manager control and Manager executor credentials are separate capabilities. Platform holds the control credential and the executor credential (for background-task stop, input, list, read and the process change feed); Runtime holds only the executor credential. Public APIs do not accept caller-supplied trusted scope identities.
- Models are not a user setting: only administrators edit model policy groups (`model_policies_v2`: a `main` and a `judge` model with thinking depths) and assign accounts to them (`users.model_policy`). Self-facing payloads (public user, bootstrap, `/api/me`) and user-visible events carry no model, group, thinking-depth, effort or judge-usage identifiers, and no self-service route changes them. Platform resolves the main model server-side for every agent usage (and the judge only with automatic depth, for titles and for judging), else the first catalog model; request bodies cannot select one. Runtime's model credential resolution authorizes the judge model id exactly like the main one. Applied effort and judge usage are recorded in admin-only usage rows and never forwarded.
- Manager remains the ingress and maintenance boundary. Keep Platform on loopback/private networking, expose no Runtime port, and use TLS at the external proxy. Rebuild forwarding headers from trusted ingress information rather than trusting client headers.

## Secrets

Platform owns Codex OAuth persistence and refresh. Runtime requests model access tokens through the authenticated resolver. Host service credentials and environment must never enter tenant sandboxes: never forward Pi's BashOperations `options.env`, mount secret directories, or embed credentials in prompts/tool output. MCP credentials (headers, OAuth tokens, stdio environment values) live in Platform only; the sandbox sees a stdio server's environment values and nothing else, Runtime and the model see none.

Secret files and Manager state remain owner-only. The database's secret flag is not encryption; backups need the same protection as live data. Avoid credentials in logs, browser previews, error messages and model context.

## Files and untrusted content

Resolve tool paths within the allowed workspace (chat file tools: conversation directory). Validate ownership and resolved paths for downloads, view tokens, `MEDIA: <sandbox cwd>/path` output and artifact publishing; a model-written path is not authorization. Built-in and organization skill directories are read-only in sandboxes.

Attachments, websites, browser pages, MCP output and workspace instructions may contain hostile instructions. They do not grant host capabilities or change authenticated ownership. Do not claim heuristic text scanning, model obedience or a confirmation dialog is an isolation boundary.

## Artifacts

An artifact is AI-authored, therefore untrusted, executable content (HTML, JavaScript, SVG) that the user opens on purpose.

- **Publishing is confined like MEDIA.** `artifact` publish takes only an absolute sandbox path under the scope's workspace, walks it with pinned directory descriptors and `O_NOFOLLOW`, never follows or copies symlinks or other non-regular files, skips `.git` and `node_modules`, and enforces 1000 files, 32 MiB per file, 50 MiB per version and a nesting limit. Only the personal, chat and channel root runs of the active job's own scope can publish; subagents cannot. The blob store holds copies, so later workspace edits or a link swapped into the workspace cannot change a published version.
- **Reading is authorized like the conversation.** The user APIs resolve the artifact's scope with the same server-side checks as the conversation's messages (private owner, chat owner, channel readers by `read_workspace`); any refusal, including a foreign artifact id, is a 404 that does not reveal existence.
- **Pages run in an opaque origin.** The view route `/artifact-view/<token>/...` answers with `Content-Security-Policy: sandbox allow-scripts allow-forms allow-modals allow-popups allow-popups-to-escape-sandbox allow-downloads allow-presentation allow-pointer-lock; frame-ancestors 'self'`. There is deliberately no `allow-same-origin`, so the document has a unique origin even when opened in its own tab: it cannot read the Platform's cookies, call authenticated Platform APIs with the user's session (its requests carry no cookies and `Origin: null`) or touch the embedding page, and the frontend's iframe repeats the sandbox attribute. The route does not authenticate by cookie at all. `Referrer-Policy: no-referrer` keeps the token out of requests to other sites, `X-Content-Type-Options: nosniff` and the exact stored MIME types stop type confusion, and `X-Frame-Options: SAMEORIGIN` plus `frame-ancestors 'self'` allow framing only by Platform's own pages. `Access-Control-Allow-Origin: *` and `Cross-Origin-Resource-Policy: cross-origin` let sandboxed pages load their own module scripts and fonts; they expose nothing beyond what the token already grants.
- **View tokens are bearer credentials.** An HMAC (session secret, domain-separated) over `{artifact id, version, expiry}` valid for 2 hours grants read access to exactly one version's files. Anyone holding the URL can read that version until it expires, the artifact is deleted or the secret changes; the token carries no identity and cannot reach any other version, artifact or API. A bad, tampered or expired token and any `..` path segment are 404. It is minted only after the same authorization as the version's other user APIs.
- **Network access from artifact pages is unrestricted, by product decision.** A page can fetch any URL and load any CDN from the viewer's browser, so a malicious or prompt-injected page can send whatever it can see to an attacker: its own content, the viewer's IP address and anything the user types into it. It sees no session, cookie or platform API, but users should treat an artifact like any untrusted web page. Sandboxed pages are served from Platform's origin; an additional origin or network restriction is not part of this design.
- **Office files render in a dedicated opaque-origin viewer.** DOCX, XLSX and PPTX (artifact versions and attachments, both tenant- or user-supplied and untrusted) are parsed by third-party JavaScript libraries, so they never run in the app origin and never in an artifact page with open network: the view URL answers with a fixed shell under `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'self'; style-src 'unsafe-inline'; img-src blob: data:; connect-src 'self' blob:; …` (no `allow-same-origin`, so no cookies or Platform APIs; no network beyond the viewer bundle and the one file; the shell contains no document content, only HTML-escaped metadata). Viewer libraries are pinned (`docx-preview` 0.4.1 with alt-chunks off and hyperlinks limited to http, https and mailto, SheetJS CE 0.20.3 with cells written through `textContent`, `@aiden0z/pptx-renderer` 1.3.0 with its recommended ZIP limits), the frontend repeats `sandbox="allow-scripts"` on the iframe, and CORS `*` (no credentials) is granted only to the viewer assets and the token-addressed bytes that an opaque origin needs. Attachment view tokens (`/attachment-view/<token>/…`, 2 h, signed, stateless, cookie-less) are minted only by an authenticated request that passes the download's ownership and scope checks, and grant read access to that one attachment. `script-src 'self'` allows same-origin scripts, and the only scripts Platform serves from `/file-viewer/` are our own build output; user files are never served as scripts to that frame. The renderer self-check loads the same shell, so its containment is unchanged.
- **Downloads** use `Content-Disposition: attachment` with `Content-Security-Policy: sandbox`, and site zips contain only snapshot files under normalized relative names.
- **A helper script runs inside every page.** Platform injects `/artifact-runtime.js` into every HTML response of the view and live routes. It runs in the page's own opaque-origin realm with the page's privileges and adds no capability: an in-memory `localStorage`/`sessionStorage`/`document.cookie` replacement, a bounded console log and an element inspector that is off until the parent asks. Storage persistence is parent-mediated: the parent seeds `localStorage` through the URL fragment and receives debounced snapshots by `postMessage`, capped at 256 KB per artifact. The parent trusts helper messages only when `event.source` is the artifact iframe's window; the helper trusts only `window.parent`. Because the page shares the realm, a page can forge helper messages (a fake pick or storage snapshot); those only reach the same user's own composer and cached storage and carry no authority. The script is a static build asset served with `Access-Control-Allow-Origin: *`; injection is bounded to HTML of 8 MiB.
- **Rendering uses a dedicated browser identity and is contained in three layers.** `artifact view` and annotate capture render a page with Camofox under a fresh identity `artifact-render:<uuid>`, never the user's own browser context, and delete the session afterwards. The URL is built by Platform from an authorized artifact version (a fresh renderer-only view token) or a running live preview; no model or user supplied URL is navigated. Navigation is the internal `http://platform:8765` (setting `AGENT_PLATFORM_ARTIFACT_RENDER_BASE_URL`), which the AI's own browser tool refuses, so the renderer is a separate trusted code path. Settling is polled from Platform with fixed synchronous expressions (no Promise, timers or iframes that page code could stall or forge) under a time budget, not Camofox's `/wait`, which can click consent dialogs. Because page JavaScript runs in an unfiltered browser on the core network, a page could otherwise navigate the tab or frame an internal service and have it photographed; the layers are (1) the tab's `location.href` must still be under the minted token or preview id after settling and after the screenshot, else the render is refused (`render_blocked`); (2) the view route answers renderer-only tokens, and live requests carrying the renderer marker, with `frame-src 'self' data: blob:; child-src 'self' data: blob:` in the CSP (ordinary viewing keeps unrestricted network, a product decision); (3) Camofox's network guard gives `artifact-render:` contexts strict egress: loopback, private, CGNAT, link-local, ULA and every other non-public address are denied, except the exact render base host in `AGENT_PLATFORM_CAMOFOX_RENDER_ALLOWED_HOSTS`, with DNS answers pinned. Screenshots are size-bounded (native clip, pixel limit) and renders are limited to 2 at once, 1 per user and 30 per user per minute. A captured screenshot is stored as the user's own pending upload.
- **Live previews expose the AI's own dev server under a capability.** `/artifact-live/<preview_id>/…` authenticates by the 128-bit random `preview_id` alone (no cookies; the page's opaque origin sends none). The capability is stable for the preview's lifetime so that a framework restarted with its base path keeps working: while the service is stopped the id answers 503, and a later process of the same service name rebinds it. Only the user's explicit stop (or deleting the artifact or conversation) revokes it; a revoked or unknown id is 404. Platform dials only Manager's executor proxy route with the id of the process bound to that preview and the owner `private:<uid>` taken from the preview row, never from the request; Manager in turn dials only that owner's own sandbox IP and the port registered at start, follows no redirects and strips credentials (see [sandbox processes](#background-tasks-and-subagents)). Platform forwards only a small request-header allowlist and drops every other upstream response header, in particular `Set-Cookie` and `Clear-Site-Data`, which would otherwise affect Platform's own origin; `Location` is rewritten under the capability prefix and any target outside the app goes to the preview root, never off Platform (no open redirect); the opaque-origin sandbox policy and `no-referrer` are applied regardless of upstream headers. HTML buffering for helper injection is bounded in time and memory and takes no update-gate admission. Anyone holding the URL can use the running app (including its own APIs and any secrets it exposes) until the preview ends; treat the link as a bearer credential. Residual risk: the proxy proves the container, not which process owns the port, and sandboxes already share the core network laterally, so a user's dev server can itself reach other core services; this change neither adds nor removes that.

## Installed skills

A skill is instructions plus scripts that the AI follows with the user's own sandbox capabilities; installing one grants no host capability, but it can steer the AI, so installed skills are as untrusted as other workspace instructions. Personal and channel skills live in the tenant workspace and are tenant-writable. Organization skills are written only by Platform for administrators (`system_settings`), are mounted read-only and are the one tier that is shared across users; built-in skills ship in the image, root-owned and world-readable.

The sandbox skills safety net runs as root at agent-sandbox start, on directories the tenant controls (workspace and home). It therefore opens each trusted root and descends one component at a time with `O_NOFOLLOW`, skips any path that crosses a symlink, performs every mkdir, rename, link and ownership change relative to those directory file descriptors, copies links as links when moving across mounts, only handles real directories, and moves displaced skills to `.agent-platform/skills-archive/` instead of deleting them. Its links and moves stay inside the tenant's own workspace and home mounts, so it grants no new access; the chat profile is excluded.

Installing, updating or removing a personal or channel skill, by the user or by the AI's `skill` tool, requires the acting user's `install_extensions` permission, checked server-side from the live permission group; without it personal skills are also not loaded into the catalog. Administrators always hold it. Downloads use the web-fetch SSRF rules (public addresses only, redirects re-validated, connections pinned to the checked address, streamed with a size cap) and archives are extracted by Platform with path-confinement, no links or devices, and file-count and size limits; the install never executes anything. Skill APIs authorize by owner: a personal skill is reachable only by its owner and a channel skill only by users who may read the channel.
## Web and browser

Web fetch accepts public HTTP(S) destinations only, with address checks repeated on every redirect, bounded time/response size and safe HTML extraction. Reject local/private/link-local destinations and unsafe schemes. Search results are untrusted URLs, not permission to access internal services. Chat web tools run through Platform; chat bash has no network. The plain request presents a desktop browser `User-Agent` and `Accept-Language`; this changes only how the request looks, never which addresses may be reached.

Page markup is hostile input and must not be able to stall Platform. Platform's own text handling is linear (script/style removal in one forward pass, line-based blank-line collapsing, a single-pass image filter for the excerpt, whitespace runs cut before markdownify). The third-party parsers (html.parser, markdownify's regexes and recursion) are not linear on every input and hold the GIL, so each conversion runs in a separate worker process with a 10 s deadline, after which it is killed; at most 3 run at once. A page that cannot be converted is a classified `unsupported` result, never an error of the gateway.

When a site blocks that request or the page needs JavaScript, Platform retries it in Camofox under a fresh identity `web-fetch:<uuid>`, never the user's own browser context, and always deletes that session afterwards. The page's JavaScript is untrusted, so Camofox gives `web-fetch:` contexts the same strict egress as artifact renderers but with no allowlisted host at all: every request, redirect, subresource and WebSocket (route guard) and every connection (the strict pinning proxy, which resolves once and connects to the checked address) must go to public addresses; loopback, private, CGNAT, link-local, metadata, multicast, reserved, documentation, NAT64 and 6to4 addresses are refused, and a name with any non-public answer is refused entirely. When Camofox runs behind an operator's upstream proxy, that proxy resolves names itself and the pinning cannot hold, so Camofox refuses to create `web-fetch:` contexts (fail closed) and Platform reports the real-browser retry as unavailable. The fallback only runs for a URL whose plain fetch already passed Platform's public-address check, reads the page with fixed synchronous expressions polled from Platform, and is bounded (2 at once across Platform, one at a time per user, 6 per user a minute, 90 s per fetch plus at most 10 s of session cleanup). The model never sees cookies or the browser session; it receives only the extracted Markdown.

Throwaway identities (`web-fetch:` and `artifact-render:`) leave nothing on disk: Camofox's persistence plugin neither restores, saves nor seeds them with the bootstrap `cookies.txt` (its session hooks never run for them), and at startup Camofox deletes any profile directory an earlier version saved for them (recognised by the `userId` in its `meta.json`; other identities' profiles are untouched).

WebRTC is disabled in Camofox (`media.peerconnection.enabled=false` at launch). STUN, TURN and ICE open UDP and TCP sockets that neither the route guard nor the pinning proxy sees, so a page could otherwise probe internal addresses. Firefox preferences are browser-wide, so this applies to every context, including the personal AI's own browsing, which has no use for peer connections; forcing ICE through the proxy (`media.peerconnection.ice.proxy_only`) was not chosen because ordinary contexts behind an operator proxy are not pinned and the pref would still leave a browser-wide WebRTC surface to reason about.

Camofox uses a Platform-derived scope identity and service authentication. Personal browser takeover is a single-holder expiring lease; agent browser actions return busy while held. Takeover grants browser interaction, not host or cross-user access.

Before each agent-requested navigation, Platform resolves the URL host and rejects metadata, link-local, multicast or reserved destinations, URL userinfo, and any address within the subnets of Platform's own container network interfaces. Platform discovers those interface subnets at runtime; shared core-network service names are therefore covered without injected CIDR configuration. Camofox's existing enforcement remains unchanged.

This check does not intercept every in-page link or redirect. Residual browser access to core services through those paths is an accepted risk, not a guarantee of network isolation; internal services still require their bearer tokens. Do not equate the navigation check with web fetch's redirect-by-redirect SSRF protection.

## Background tasks and subagents

Personal AI only; channels and chat have no such tools, and a subagent session cannot reach the `tasks` gateway (its session is not a root personal session).

- Ownership: a task row belongs to one user. The user API and the AI's `job`/`wait` tools resolve a task only through its owner; another user's or a foreign task id is "not found", and API calls need `private_agent`. Process ids from Runtime are accepted only if Manager lists them under the caller's own owner scope (`private:<uid>`).
- Stop and input are real executor operations: Platform requests a one-shot audit receipt (operation `process`, action `kill` or `stdin`; stdin audit records the process id and byte count, never content), then calls Manager. A process counts as `stopped` only after Manager confirms termination; an unconfirmed kill leaves the task `running` and is reported as an error.
- Subagents share the parent's sandbox and workspace, so they are not isolated from it or from each other. Their tool set is fixed by Platform (`scout`: read, grep, find, ls, web search/fetch; `task`: additionally bash, edit, write), they run foreground commands only and cannot spawn subagents. Limits: 8 running subagents and 16 running processes per user.
- Recovery: a subagent whose Runtime stream is lost, or that was running when Platform restarted, becomes `interrupted` and is never replayed (Platform only cancels any still-live child run). A Manager restart stops every sandbox, so running processes become `interrupted` (`system_restart`); commands are never rerun. Results of finished tasks reach the AI exactly once: `delivered_at` is set atomically by `wait` or by the notice worker, and a notice whose tasks were already delivered is skipped. Task results are untrusted tool output: the notice prompt escapes them inside a `<background-task-results>` block and they carry no authority.

## Effects and recovery

Cancellation stops future work but cannot undo completed external effects. A lost/failed run becomes visibly interrupted; do not replay it automatically. Executor audit receipts are one-shot and identity-bound. Removed approval/review systems must not be recreated as retry or completion heuristics; background work follows [its own rules](#background-tasks-and-subagents).

Manager accepts sandbox foreground terminal execution, supervised background
processes (`operation:"process"` receipts for start/stdin/kill; stdin audit
records the process id and byte count, never content) and confined file
read/write. Timeout, kill and cancellation terminate and confirm the sandbox command
process group, including grandchildren; stopping the host Docker client alone is
not confirmation. Foreground commands have in-memory run ownership. Background
processes are owned by the scope-family root of the creating call; read-only routes
require the matching owner, and foreign ids are indistinguishable from missing ones.
Their combined output passes through the same incremental redactor before it is
written to the capped log (`<manager state>/processes/<id>/output.log`, owner-only);
commands shown in views are redacted. A named service that declares a `port` is reachable through the executor proxy route (`/v1/executor/proxy/…`, [contract](../reference/runtime-api.md#sandbox-service-proxy)). The destination is never caller-supplied: Manager dials only the owner's own sandbox container IP on the core network (ownership labels re-proved at least every 30 s and after any failed dial) and the port recorded at start, follows no redirects, strips credentials and forwarding headers, and ends requests and WebSocket tunnels when the process ends; streams are capped per owner. Residual risk: the proxy proves the container, not which process in it owns the port, and sandboxes already share the core network laterally; the executor credential is a service credential, so the owner is a trusted assertion as for the other process routes. Process records survive a Manager restart as
history only: running processes become `interrupted` (`system_restart`) and are never replayed.
Before executor readiness on every Manager startup, all running managed sandbox
containers are stopped. Failure to confirm cleanup prevents executor readiness.
Sandbox workspace, home and environment are retained and restart on demand.
MCP stdio servers run only in a personal sandbox through a dedicated Manager
channel (`operation:"mcp"` receipts for start/send/stop). Platform alone holds
the MCP credentials: environment values travel to Manager in the receipt-bound
start body, are handed to the in-sandbox supervisor over its control pipe, and
never appear in argv, process records, logs or audit (the audit projection is
`{connector_id, command, args_count, env_keys}`, `{connection_id, bytes, method?}`
and `{connection_id}`). The server's stdout is a protocol stream: it is never
redacted, never written to disk and is held in an 8 MiB in-memory queue per
connection (frames ≤ 1 MiB, an overflow or an oversized or non-UTF-8 frame ends the
connection with a reason); its stderr alone goes through the redactor into the
capped log. A connection holds its sandbox resident only while a start or send is
in flight, so an idle stop, a sandbox stop or a Manager restart kills it and Platform
reconnects lazily without replaying a `tools/call`. Limits are 8 per owner and 64
globally; a foreign or unknown connection id is 404.

## MCP connectors: custody, scopes and audit

- **Credential custody.** Header values, stdio environment values, OAuth tokens and registered clients live in `mcp_secrets`, written through Platform only. No API, SSE event, tool result, audit row, log or error returns a value; views report `secrets_set: {key: bool}`. The AI cannot supply secrets (the `mcp` tool rejects values in `add`; secrets arrive from the user's secure form). Runtime receives tool definitions and results, never credentials; a stdio server receives only its own environment values, passed through Manager's channel.
- **Confirmation before credentials.** A connector the AI added or imported, or one imported from a workspace file, starts `pending_confirmation`: Platform never connects it, offers it to a run, tests it or accepts credentials for it until its owner confirmed, in a card or in settings, the destination it shows (URL origin, or command line). This stops a prompt-injected instruction from sending the user's key or sign-in to an attacker's server.
- **Server-side authorization.** Platform recomputes availability from the database on every gateway call (the run payload is advisory): the connector must be enabled, assigned to the user's permission group (organization), owned by the user and the user must hold `install_extensions` (personal), enabled for the channel with shared credentials (channels), remote (chat) and, for subagents, of a type that may use the tool (`scout`: read-only tools only). Per-user and personal credentials are isolated per account (one connection per connector and credential owner); a shared credential acts as the account that connected it, so administrators connect shared connectors deliberately and only channel managers can expose them to a channel. Management actions (`add`, `remove`, `import`, `connect`, `enable`, `disable`) are personal-root only and need `install_extensions`.
- **Fixed error messages.** Connection failures reach users, the AI and the log as a fixed category (or the exception class name), never exception text, which can carry URLs, header values or server-chosen content. Header and environment values are trimmed and must not contain control characters or line breaks (header injection). The one server-authored string passed on is the JSON-RPC error message of a failed call, with control characters removed. Tool names must match `[A-Za-z0-9_.-]{1,128}`; control and line-separator characters are stripped from everything listed in the deferred catalog.
- **Untrusted output.** Tool results, resources, prompts, tool descriptions and server instructions are untrusted data that may carry hostile instructions; they never change authenticated ownership or grant capabilities. Output is bounded (text 200 KB, images 4 × 2 MiB, SSE events 1 MiB, responses 4 MiB). Elicitation forms and links are shown as the server sent them: nothing is accepted automatically, only the user who triggered the run can answer, and a timeout is a cancel. Elicitation URLs must be http(s).
- **Audit.** Every call (tools, resource reads, prompt renders) writes who, connector, tool, status and duration to `mcp_calls`, never arguments or results; the latest 10,000 rows are kept. A `tools/call` whose delivery is uncertain is never replayed.
- **Imports and detection.** Foreign configuration is parsed in Platform (bounded, no execution); workspace files are only offered, never enabled automatically, and are read through descriptors that never follow symlinks. Literal secrets found in an import move into `mcp_secrets` and are not echoed back.

## Remote MCP: network policy and OAuth

Every byte Platform exchanges with a remote MCP endpoint, protected-resource metadata, authorization-server metadata, registration or token endpoint goes through one guarded httpx2 client (`mcp/net.py`; the official SDK speaks httpx2, so it is a second guard next to the web-fetch one). It accepts http(s) URLs without userinfo only. Every address a host resolves to must be public; one disallowed address in an answer refuses the whole answer. The administrator setting `mcp_private_networks_v1` (CIDRs, host names, `*.suffix`) waives the "public" requirement for organization connectors only; personal connectors, which any user may create, stay public-only. Even allowlisted, loopback, link-local, multicast, reserved and unspecified addresses, cloud metadata addresses and names, Platform's own service names (`platform`, `agent-runtime`, `camofox`, `searxng`, the Manager) and Platform's own interface subnets are refused, and a host name entry never skips the address checks. The TCP connection is pinned to an address that passed the check, while the Host header and the TLS server name stay the original name, so a name re-resolved to a private address after the check cannot redirect the connection. Each redirect hop opens its own checked connection, so a redirect to a private address is refused. Unix sockets and environment proxies are never used. Connecting is capped at 10 s. Requests ask for identity encoding and a response with any `Content-Encoding` is refused, so a compressed bomb cannot expand past the cap; every response is capped at 4 MiB (and 60 s for its body). Only a request to the connector's own MCP endpoint may answer with an event stream, which is capped per event (1 MiB) and per silent period instead of in total; an event-stream content type on a metadata, registration or token request is capped like any body. A blocked destination fails with the typed `mcp_network_blocked`.

OAuth uses the SDK `OAuthClientProvider` on that client with Platform-owned storage; the tokens, the registered client and the discovered authorization-server metadata live in `mcp_secrets`, never in an API response or a log, never in Runtime or a sandbox. Tokens are bound to (connector, owner, issuer): per-user and personal connectors store them under the user, shared connectors under no user, and a token whose recorded issuer differs from the verified authorization server is never presented. A pre-registered client entered by an administrator binds to the first issuer it is used with and is refused for any other. Platform advertises `application_type: web` with the redirect URI `<public_base_url>/api/mcp/oauth/callback`. Client registration follows one order: the stored pre-registered client, then a client-ID metadata document (`<public_base_url>/api/mcp/oauth/client.json`) only when the public address is https and the server advertises support, then dynamic registration only when `registration_endpoint` is advertised (a `/register` path is never guessed), otherwise the typed `oauth_registration_required`, which the administrator resolves with a client id and secret. An authorization server that does not advertise S256 PKCE is refused (`oauth_pkce_unsupported`), before anything is registered. OAuth needs `public_base_url` to be https or loopback (`oauth_https_required`; connector views carry `oauth_warning: "https_required"` otherwise).

Interactive authorization is a pending flow in Platform memory keyed by the unguessable `state`, valid for 10 minutes, single use, and bound to the user who started it: a callback with an unknown, replayed or expired state, another user's session, or an authorization-server `iss` that does not match the issuer fails and exposes nothing. The authorization URL handed to the browser must be https (or http on loopback). A connector that needs authorization again reports the typed `needs_auth` with HTTP 409, never 401, which the frontend treats as a lost session. A Platform restart drops pending flows and the user connects again. The callback page is static, carries a nonce-only content-security-policy and shows only Platform-authored text (errors are cut before any server-supplied body or value). Normal calls never start a flow: the non-interactive provider refreshes an expired token, refreshes and retries once after a 401, and otherwise reports `needs_auth`. A refresh the server rejects permanently deletes the stored tokens; a transient failure keeps them. Disconnecting deletes the owner's tokens and cancels any pending flow.

Manager update reservations block new work before migration and release only through the existing owner-bound commit/abort protocol. Migrations are ordered and forward-only. See [operations](../operations/auto-update.md) and [API contracts](../reference/platform-api.md).
