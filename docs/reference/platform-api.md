# Platform API (Pi-native)

All paths are same-origin. JSON requests/responses; errors `{ "error": "message" }` with appropriate HTTP status. Auth is an HttpOnly SameSite=Lax signed `agent_platform_session` cookie, preserving installed sessions across upgrade and rollback. Mutations require same-origin requests. IDs are integers except chat conversation IDs (UUID strings). Dates are ISO 8601 UTC strings. Lists are objects, not bare arrays.

## Auth and bootstrap
- POST `/api/auth/login` `{username,password}` → `{user}`; POST `/api/auth/logout` `{}` → `{ok:true}`.
- Login failures use bounded 15-minute client/account counters; throttled requests return 429 before password hashing for exhausted client/pair budgets. Password changes require current-password proof (missing or wrong returns 400) and issue a fresh installed-session cookie.
- GET `/api/bootstrap` → `{user,branding,permissions,channels}`.
- GET/PATCH `/api/me` (patch `{display_name?,timezone?,password?,current_password?}`) → `{user}`. Changing `password` requires valid `current_password`; success renews the caller's cookie while revoking older copies.
- User (self-facing: bootstrap, login, `/api/me`): `{id,username,display_name,role,position,permission_group,timezone,active}`. Users never receive a model, model policy group or thinking depth; there is no self-service route for them. Passwords never returned.
- Branding: `{product_name,agent_name,primary_color,logo}`. Permissions: string array. Admin receives all permissions.
- GET `/api/branding` is public and returns `{branding}` for the login page.

## Personal AI and channels
- GET `/api/channels` → `{channels:[{id,name,description,archived}]}`; POST same `{name,description?}` → `{channel}`; PATCH/DELETE `/api/channels/{id}` → `{channel}` / `{ok:true}`.
- GET `/api/conversations/{scope}/messages?before=<id>&limit=100` → `{messages,next_before_id,last_seq,compaction}`. Scope is `private` or `channel-<id>`. `compaction` is the latest manual-compaction status described below, or null.
- POST same `{content,attachment_ids?:[],mode?:"insert"|"after_turn"}` → HTTP 202 `{message,job_id}`. `mode` defaults to `insert`: an eligible message joins the active interactive run as described below, otherwise it queues FIFO. `after_turn` is never inserted: it always queues FIFO and runs as its own turn after the current work, and its metadata carries `send_mode:"after_turn"`. Any other `mode` returns 400. Empty content is accepted when authorized attachments are supplied.
- DELETE `/api/conversations/{scope}/messages/{id}` withdraws a message the AI has not yet seen; see [Withdrawing a message](#withdrawing-a-message).
- POST `/api/conversations/{scope}/cancel` → `{ok:true}`; POST `/api/conversations/{scope}/reset` → `{ok:true}`.
- POST `/api/conversations/{scope}/compact` → HTTP 202 `{ok:true,job_id,status:"queued"}`. Manual compaction is a durable operation in the same per-session FIFO as messages; existing work finishes first and later messages wait behind it. The Runtime compaction request has a 15-minute timeout.
- GET `/api/conversations/{scope}/events?after=<seq>` → SSE.
- Message: `{id,role:"user"|"assistant"|"system",content,metadata,created_at,attachments:[]}`. Metadata includes `status:"queued"|"running"|"completed"|"interrupted"|"cancelled"`, optional error. Inserted user messages add `inserted_into:<request message id>` and `delivery:"pending"|"delivered"`; messages sent with `mode:"after_turn"` carry `send_mode:"after_turn"`; assistant replies add `reply_to:{message_id:<request message id>}`. Message payloads never carry the legacy metadata keys `generation` or `token_usage`; model usage is recorded only for administrators in token usage events.

### Mid-run insertion

A newly accepted message joins the scope's current turn only when its `mode` is `insert`, it is not a schedule occurrence, the current job is a running interactive message (not compaction or a schedule occurrence), the scope is not cancelling, and no other job is queued. This applies to personal AI, standard chat, and any channel member with chat permission. The inserted prompt includes attachments and the inserting author's display name and timezone.

An inserted message and its linked durable job are `running`, with `delivery:"pending"`. Runtime delivers all pending inputs in acceptance order at the next step boundary. Delivery changes metadata to `delivery:"delivered"` and emits `message`, then `input_delivered {message_id}`; the reply's work trace records that same boundary. Until delivery, the AI has not yet seen the input.

Parent settlement and all child settlements are atomic. Delivered children take the parent's terminal message status and receive no assistant reply of their own. On normal completion, accepted but undelivered inputs return to FIFO in job-id order, with `inserted_into` and `delivery` removed. On failure, cancellation, stream loss, or Platform restart, children take the parent's terminal status instead; uncertain work is never automatically resent. A definite Runtime rejection before delivery returns the child to the queue. Stop cancels the active turn, its children and queued work as before.

History pages remain id-ordered. Readers group a loaded request immediately before its `reply_to` reply, order answered turns by reply id, then show the running turn and queued work. Inserted messages render inline at work-trace input markers (pending messages at the live reply's end), never a second time at their standalone id position. Other messages retain their id position.

### Withdrawing a message

Withdrawal needs the same scope, permission and ownership as sending; in a channel only the message's author may withdraw it (403 otherwise; an unknown message is 404; a message that is not a user's own request, such as a schedule occurrence, is 400). It succeeds only while the AI has not seen the message: (a) its own job is still `queued` (FIFO or after-turn); (b) it joined a running parent but was not yet submitted to Runtime; or (c) it was submitted but not delivered, and Runtime removes it from the run's pending inputs (`DELETE /v1/runs/{run_id}/inputs/{input_id}`). Platform serializes withdrawal with sending and worker start under the scope lock, and Runtime arbitrates delivery, so each message ends either withdrawn or delivered/started, never both.

On success the job finishes `cancelled` and never runs, the user message row and its attachment links are deleted (the uploaded files stay owned by the uploader, so they can be attached to a new message by id), the scope's stream emits `message_removed {message_id}`, and the response is HTTP 200 `{content,attachments:[…]}` with attachments in the same shape as `POST /api/attachments` returns. Otherwise the response is HTTP 409 `{error:"already_seen"}`: the message is delivered, running, settled, or Runtime reports the input delivered or the run closed. If Runtime cannot be reached or answers unexpectedly the response is 502 and nothing changes. Stop is unchanged: it cancels the whole scope backlog, queued messages included.

### Assistant message work trace

Assistant messages may include `metadata.work` v1. It is stored only in the assistant message metadata, not a separate work table; the terminal `run_end.message` and history pages expose the same object:

```json
{
  "v": 1,
  "started_at": "2026-10-01T09:00:00+00:00",
  "ended_at": "2026-10-01T09:00:03+00:00",
  "items": [
    {"type": "thinking", "text": "Inspect the report first.", "started_at": "2026-10-01T09:00:00+00:00", "ended_at": "2026-10-01T09:00:01+00:00"},
    {"type": "text", "text": "I will read the report."},
    {"type": "tool", "id": "call_1", "name": "read", "args": {"path": "report.txt"}, "status": "done", "output": "Revenue increased.", "started_at": "2026-10-01T09:00:01+00:00", "ended_at": "2026-10-01T09:00:02+00:00"}
  ],
  "truncated": false
}
```

- Times are ISO-8601 UTC. Items retain arrival order; consecutive text deltas merge. Each `thinking_start` opens a separate `{type:"thinking",text,started_at,ended_at}` item; its `thinking_delta`s append text and `thinking_end` sets `ended_at`. An empty block retains both timestamps; `ended_at` is null while open or if the run ends before `thinking_end`. Deltas without an open block use consecutive-item merging, without timestamps, for older Runtime/providers. The final answer is `message.content`, never repeated in work: text items after the last tool or input item are dropped (including all text items if there is neither). Text before an input marker remains work even if it previously looked like a final answer.
- Tool fields are `type:"tool"`, `id`, `name`, `args`, `status`, `output`, `started_at`, and `ended_at`. Status is `done`, `error`, or `cancelled`; unfinished tools become `cancelled` at termination, with `ended_at:null`. Output previews use text parts from Runtime tool results, including partial updates when interrupted.
- A `bash` tool item that Runtime promoted to a background process adds `background:{task_id:"bg-<n>",process_id}` (taken from the `tool_end` details); the item's own status stays final at promotion. The `task` tool's item is linked to its subagents by `created_by_tool_call_id` on their TaskViews.
- Input fields are `{type:"input",message_id,at}`. Each marks delivery of an inserted user message and divides work into segments around its user bubble. Use the loaded user message for the bubble; if unavailable, retain only the segment break.
- Bounds apply during streaming: each thinking item is at most 16,000 characters and each text item at most 4,000; tool args JSON is at most 2,000 characters or is replaced with `{"_preview":"<first 2,000 chars of the JSON>"}`; tool output is at most 2,000 characters; at most 200 items and at most 96 KiB of UTF-8 JSON for the whole object. Open thinking blocks and tools reserve space for end timestamps. Input markers reserve space by evicting non-input work and survive truncation. If input markers alone exceed either whole-trace bound, retain them all: a delivered user message must never disappear from its reply. `truncated:true` means any bound applied.
- Omit `work` if no items remain. Completed, failed (exposed as `interrupted`), cancelled and interrupted runs retain whatever work arrived, including a Platform interruption after partial streaming.
- Older messages may carry `metadata.agent_work.activity` from the previous system. Render those records read-only, without restoring removed actions. Older releases ignore the unknown `work` metadata key; the Pi-native reader before `af47c14` decodes and returns the metadata object without a closed-key schema. No database schema migration is required.

## Standard chat
- GET `/api/chat/conversations` → `{conversations:[Conversation]}`; POST same `{title?}` → `{conversation}`.
- GET/PATCH `/api/chat/conversations/{id}` → `{conversation}` (patch `{title?}`); DELETE same → `{ok:true}`.
- Conversation: `{id,user_id,title,created_at,updated_at,deleted_at:null}`. Any other request field, including `model_id`, returns 400; there is no chat model endpoint and users cannot select a model. Titles are never generated automatically: a new conversation is titled by the client (`{title?}`, default `New chat`) and renamed only by explicit PATCH.
- GET/POST `/api/chat/conversations/{id}/messages`, DELETE `.../messages/{message_id}` (withdraw), GET `.../events`, POST `.../cancel`, POST `.../compact`: same shapes as agent conversation routes. Chat tools are only Pi built-ins, web search/fetch and `artifact`. The chat model and thinking depth come from the `chat` slot of the account's model policy group.
- One chat sandbox is shared by all conversations of one user (`chat-user-<id>`, profile `chat`). The security boundary is the user. File tools reject paths outside `/workspace/<conversation_id>`; bash starts there but may access that same user's other conversation files. Conversation deletion removes its directory and its [artifacts](#artifacts).

## SSE
Each event uses `id: <seq>`, `event: <type>`, `data: <JSON>`. Event object includes `{seq,type,...}`. Types: `message {message}`, `text_delta {delta}`, `thinking_start {}`, `thinking_delta {delta}`, `thinking_end {}`, `tool_input_start {tool_call_id,name}` (the model began a tool call; precedes `tool_start`), `tool_input_delta {tool_call_id,delta}` (raw argument-JSON fragments in order; their concatenation is partial until `tool_start`), `tool_start {tool_call_id,name,args}` (authoritative arguments), `tool_update {tool_call_id,partial}`, `tool_output {tool_call_id,delta,truncated?}` (live bash output appended in order, at most 512 KiB per call, then one event with `truncated:true` and an empty delta; `tool_end` stays authoritative), `tool_end {tool_call_id,name,is_error,content_preview,details}`,…
`input_delivered {message_id}` marks the inserted user's position within the live reply. `message_removed {message_id}` announces a withdrawn message: drop it from the transcript. Platform does not expose Runtime input/job IDs or `undelivered_inputs`; message updates expose settlement instead. Every child metadata/status change emits its own `message` event.
`mcp_action_required`, `mcp_elicitation` and `mcp_elicitation_resolved` (see [MCP](#mcp)) are durable conversation events like the others.
`artifact {artifact:ArtifactView,version}` announces a newly published artifact version in a personal, chat or channel conversation (see [Artifacts](#artifacts)); it is durable and replayed like the other events.
Message pages are ascending by id; `next_before_id` is null at the oldest page. SSE sequences are globally monotonic, durable, and filtered by authorized scope. Without `after`, events replay from the beginning; reconnect with the latest sequence. User messages broadcast when queued; assistant messages are inserted only at termination, including interruption.
The page `last_seq` watermark is the active job's starting sequence, or the current scope maximum while idle; use it for the initial SSE `after` to recover partial output without replaying old runs. Last-Event-ID wins over the query parameter on reconnect. User message metadata includes `author_user_id` and `author_display_name`, and `message` also announces transition to running. Reset, chat deletion and chat updates return 409 while busy; cancel first. Manual compaction instead joins the FIFO.
Manual compaction emits `compaction` events with `{phase:"queued"|"start"|"end",job_id,status,reason?,error?,after_message_id?}`. Status is `queued`, `compacting`, `done`, `nothing_to_compact`, `interrupted`, or `cancelled`; `nothing_to_compact` carries `reason:"too_small"` and is a successful no-op, not an error. `after_message_id` is the operation's place in the transcript: the newest message when it started (or settled without starting), excluding user messages still queued behind it; `null` for an empty conversation; absent while queued. The messages-page `compaction` object retains `{job_id,status,reason?,error?,after_message_id?}` for reloads. Manual compaction creates no artificial conversation messages. Automatic compaction during a model run retains its existing `compaction {phase:"start"|"end",reason}` events.
Open event streams recheck the signed session and current authorization before emitting each batch; revocation terminates the stream. After uncertain submission or stream loss, the interrupted prompt is never resubmitted. Platform cancels and settles any still-live run for that session, even without a successor job; uncertain work continues blocking Manager readiness until settled. After a Runtime restart there may be no live run to cancel: Platform continues the queue; untracked Manager commands are not reclaimed and expire under their finite command timeout.

## Attachments and workspace
- POST `/api/attachments?scope=private|channel-<id>|chat-<uuid>` multipart field `file` → `{attachment}`. Attachment `{id,filename,mime_type,size_bytes,url,preview_url}`.
- GET `/api/attachments/{id}` authenticated download; GET `/api/attachments/{id}/preview` image/document preview.
- Previews: images return PNG thumbnails; PDF returns inline PDF with a sandbox policy; DOCX/XLSX/PPTX and text return bounded `text/plain` previews. Other formats have `preview_url:null`. Originals live outside tenant-writable workspaces; copies for model tools are made into scope uploads. Uploads are limited to 32 MiB each; aggregate inline image data is limited to 12 MiB before message acceptance.
- GET `/api/workspace/files?path=` → `{files:[{name,path,is_dir,size_bytes}]}`; GET `/api/workspace/download?path=` authenticated download. Paths relative to personal workspace.
- Agent `MEDIA: <sandbox cwd>/path` output creates normal authorized downloadable attachments, except for the previewable text kinds (`.html`, `.htm`, `.md`, `.markdown`, `.svg`, `.mmd`, `.mermaid`, `.csv`, `.tsv`), which publish an [artifact](#artifacts) version instead of an attachment. Images, PDFs, Office files and every other extension stay attachments.
`MEDIA:` lines remain in message content for compatibility; attachments are additionally rendered as download links.

## Artifacts
An artifact (作品) is identified by `(scope, path)`: the scope is the personal AI (`private`), a chat (`chat-<conversation id>`) or a channel (`channel-<id>`), and `path` is the absolute sandbox path the AI published (a file, or a folder for a website). `kind` is derived from the entry extension: `web` (`.html`, `.htm`), `site` (a published folder; entry defaults to `index.html`), `markdown` (`.md`, `.markdown`), `mermaid` (`.mmd`, `.mermaid`), `svg`, `table` (`.csv`, `.tsv`), `image` (png, jpg, jpeg, gif, webp), `pdf`, or `code` (common text and source extensions). Anything else is refused with `artifact_unsupported_kind`, which tells the AI to use `MEDIA:` for downloads.

A **version** is an immutable snapshot of a manifest `{relpath:{sha256,size,mime}}` plus `entry`. Each publish of changed content creates version `latest+1`; content identical to the latest version (same manifest and entry) creates none. File bytes are content-addressed blobs under `<data_dir>/artifacts/blobs/<sha256>`, shared by every version and scope that holds the same bytes. A snapshot is the file, or the directory tree walked with pinned directory descriptors and `O_NOFOLLOW`: symlinks and other non-regular files are never followed or copied, and `.git` and `node_modules` directories are skipped at any depth. Limits per version: at most 1000 files, 32 MiB per file, 50 MiB in total and 24 directory levels; exceeding one fails the publish (`artifact_too_many_files`, `artifact_file_too_large`, `artifact_too_large`, `artifact_too_deep`) and stores nothing. The published path must be an absolute sandbox path under the scope's workspace (the same prefix rule as `MEDIA:`; the chat cwd is `/workspace/<conversation id>`); `//` and `.` segments are normalized and `..` is refused (`artifact_path_invalid`). A missing path, a path through or onto a symlink, or an unreadable one is `artifact_path_not_found` or `artifact_path_invalid`. A folder without its entry file is `artifact_entry_not_found`.

**ArtifactView** `{id,scope,path,kind,title,entry,latest_version,created_at,updated_at}` (`entry` is the latest version's entry; `title` is the publish `title`, else the file or folder name without extension, and a later explicit title renames it).

**Publishing.** The runtime tool `artifact` calls the internal gateway `POST /internal/agent/tools/artifacts` `{action,arguments,context}` (same bearer and context as the other gateways; personal, chat and channel root runs only, subagent sessions get 403). Actions: `publish {path,title?,entry?}` → `data:{artifact,version,created}` with text saying it was published as version N (or that it equals version N and no version was created) and that the user can open it in the artifact panel; `list` → `data:{artifacts:[ArtifactView]}` for this conversation. Business failures are `is_error:true` with `data.error` set to the typed code. Each version records the durable job (`job_id`) of the run that created it.

**Event and message link.** Every created version emits an `artifact {artifact:ArtifactView,version}` event on the conversation's event stream, so an open live reply shows the card at once. When the run's assistant message is persisted, Platform sets `message_id` on the versions created in that run (tool publishes and MEDIA publishes) and adds `metadata.artifacts:[{id,version,title,kind,path}]` to the assistant message, in publish order; the `run_end` event's `message` already carries it. A reply that published nothing has no `artifacts` key.

**User APIs**, authorized like the conversation's messages: the personal owner (`private_agent`), the owner of a chat, and channel readers (`read_workspace`); every refusal, including another user's id, is HTTP 404.

| Route | Response |
| --- | --- |
| GET `/api/artifacts?scope=private\|chat-<cid>\|channel-<id>` | `{artifacts:[ArtifactView]}`, newest update first; `scope` defaults to `private` and is checked like the conversation APIs |
| GET `/api/artifacts/{id}` | `{artifact,versions:[{version,entry,created_at,total_size,file_count,message_id}]}`, newest version first; `message_id` is null until the run's reply is persisted |
| GET `/api/artifacts/{id}/versions/{v}/files` | `{entry,files:[{path,size,mime}]}` sorted by path |
| GET `/api/artifacts/{id}/versions/{v}/source?path=` | `{content,truncated,mime}` for a text file of that version (`path` defaults to the entry); at most 2 MiB, cut on a character boundary with `truncated:true`; other files are 415 `artifact_not_text` |
| GET `/api/artifacts/{id}/versions/{v}/download` | the single file, or for a `site` a zip of its tree (`<folder>-v<N>.zip`), with `Content-Disposition: attachment` |
| POST `/api/artifacts/{id}/versions/{v}/view` | `{url:"/artifact-view/<token>/<entry>",expires_at}` |

**View tokens.** `<artifact id>.<version>.<exp>.<signature>`, where the signature is an HMAC-SHA256 with the Platform session secret (domain-separated) over the first three fields and `exp` is 2 hours after minting. A token grants read access to exactly that version; it is a bearer credential that carries no user identity, and it stops working when the artifact is deleted or the secret changes.

**GET `/artifact-view/<token>/<path…>`** serves a version's files with no cookie authentication. A bad, tampered or expired token, an unknown version or file, and any path with a `..` segment is HTTP 404. An empty path serves the entry; a directory path serves its `index.html` (a directory path without the trailing slash redirects, 307, to the slashed form so relative URLs resolve). Relative URLs inside a site therefore resolve under the same token prefix. Headers on every served file: `Content-Security-Policy: sandbox allow-scripts allow-forms allow-modals allow-popups allow-popups-to-escape-sandbox allow-downloads allow-presentation allow-pointer-lock; frame-ancestors 'self'` (no `allow-same-origin`, so the document has an opaque origin even in its own tab), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Access-Control-Allow-Origin: *`, `Cross-Origin-Resource-Policy: cross-origin` and `Cache-Control: private, max-age=7200`. Text types (`text/*`, JSON, XML, SVG) are served with `charset=utf-8`. Platform's default headers (`Referrer-Policy: same-origin`, nosniff, `X-Frame-Options`) apply only where a handler did not set its own. Pages may reach any network address (see [security](../design/security-and-trust.md#artifacts)).

Deleting a chat deletes its artifacts and versions and then every blob no remaining version references (blob collection happens only at deletion). Personal and channel artifacts persist with their scope.

## Browser (personal AI only)
- GET `/api/browser` → `{tabs:[],lease:{holder_user_id,expires_at}|null}`.
- POST `/api/browser/action` `{action,arguments:{},holder_id}` → `{content,data,is_error}`.
- POST `/api/browser/lease` `{holder_id:"per-tab UUID"}` → `{lease}` (acquire/renew, 60 seconds); DELETE same with `{holder_id}` → `{ok:true}`. Another holder (including another tab of the same user), or agent action during takeover, returns HTTP 409.
- GET `/api/browser/screenshot?tab_id=` → PNG.
- Browser actions include `new_tab {url}`, `navigate {tab_id,url}`, `click {tab_id,x,y}` or `{tab_id,ref}`, `type {tab_id,text,mode:"keyboard"}` (without a ref), `press {tab_id,key}`, `scroll {tab_id,direction,amount}`, `back|forward|refresh {tab_id}`, `snapshot {tab_id}`, and `close {tab_id}`. New tabs return Camofox `tabId`; tab lists retain Camofox tab objects. Screenshot coordinates are viewport pixels.
- Navigation permits ordinary LAN targets but rejects dangerous address ranges, credential-bearing URLs and the Platform container's own interface subnets. This entry-point check does not intercept every in-page redirect/link; see the documented residual risk in [security and trust](../design/security-and-trust.md).

## Skills
Tiers, paths, catalog rules and package limits are in [data and skills](../design/data-memory-sessions.md#skillmd-skills). Errors are `{error, code?, ...}`; typed codes: `skill_exists` (409; the name is installed and `replace` was not set), `skill_candidates` (409; an archive or repository holds several skills and no `subpath` was given; `candidates:[{name,subpath}]`), `install_extensions_required` (403), `skill_invalid` (400; validation, size, unsafe archive entry), `skill_not_found` (404), `skill_update_renamed` (409; the source now names a different skill: `name` is the requested name, `new_name` the fetched one; nothing changes), `skill_not_updatable` (400), `skill_fetch_failed` (502; download failed, including the SSRF refusal as 400).
- SkillView: `{key:"builtin:<n>"|"org:<n>"|"personal:<n>"|"channel:<id>:<n>",name,description,tier:"builtin"|"org"|"personal"|"channel",version|null,source:{kind:"upload"|"url"|"workspace"|"ai"|"migrated",url?}|null,enabled,user_disableable,manageable,updated_at|null,warnings:[string]}`. `source` is null for built-in and organization skills. `enabled` is the viewer's effective on/off (user preference for personal/chat; for the shared channel scope it is true). `user_disableable` is false in a channel scope. `manageable` is true for the viewer's own personal skill when they hold `install_extensions`; channel skills are managed only through the AI's `skill` tool.
- GET `/api/skills?scope=private|chat|channel-<id>` (default `private`; needs `private_agent`, `chat`, `read_workspace` respectively) → `{skills:[SkillView],can_install}` using the catalog's visibility rules, except that skills hidden from the model by `disable-model-invocation` and the viewer's own disabled skills are still listed (`enabled:false` for the latter). `can_install` is `install_extensions`.
- GET `/api/skills/{key}` → `{skill,content,files:[{path,size_bytes}]}` (`content` is SKILL.md text, at most 256 KB). A personal key is readable only by its owner and a channel key by users who may read the channel; a caller with `system_settings` may read any organization skill, assigned or not.
- POST `/api/skills` installs a personal skill (needs `install_extensions` and `private_agent`): multipart `file` (zip or `.skill`, at most 50 MB) with optional `subpath`, `replace`; or JSON `{url,subpath?,replace?}` → `{skill}` (201). Install, update and read responses apply the user's own preference to `enabled` and never change it.
- POST `/api/skills/{key}/update` → `{skill}` (re-fetches the recorded `url` source; other sources 400). DELETE `/api/skills/{key}` → `{ok:true}`; personal skills only. PUT `/api/skills/{key}/preference` `{enabled}` → `{skill}` for any skill the user sees (not channel keys).
- Administrator (`system_settings`): GET `/api/admin/skills` → `{org:[SkillView+{groups,enabled}],builtin:[SkillView+{org_enabled}],groups:[names]}`; POST `/api/admin/skills` (multipart or JSON as above plus `groups`, default `["*"]`) → `{skill}`; PATCH `/api/admin/skills/{name}` `{enabled?,groups?}` → `{skill}`; POST `/api/admin/skills/{name}/update` → `{skill}`; DELETE → `{ok:true}`; PUT `/api/admin/skills/builtin/{name}` `{enabled}` → `{ok:true}` (setting `builtin_skills_disabled_v1`). `groups` is `["*"]` or existing permission-group names.
- Gateway: POST `/internal/agent/tools/skills` `{action,arguments,context}` with action `list`, `info {name}`, `install {url|path|content, subpath?, replace?}`, `update {name}`, `remove {name}`; personal and channel root runs only (not chat, not subagents). Install, update and remove act on the run's scope and need the triggering user's `install_extensions`. A message that starts with `/<skill-name>` of the scope's catalog (hidden skills included) is sent to Runtime prefixed with the invocation sentence, for the first prompt and for inserted inputs.
## MCP
Design: [integrations](../design/integrations.md#mcp). Errors are `{error, code?, ...}`; typed codes include `invalid_connector`/`invalid_name`/`invalid_groups`/`unknown_field`/`unknown_secret` (400), `name_in_use` (409), `connector_not_found` (404), `permission_denied` (403), `not_connected` (409), `confirmation_required` (409), `needs_auth` and `credentials_rejected` (409; upstream authorization failures are never HTTP 401, which the web app treats as session expiry), `connect_failed`/`mcp_error` (502), `connect_timeout`/`call_timeout` (504), `mcp_network_blocked` (400), `import_unrecognized`/`import_invalid` (400), `import_not_found` (404), `oauth_registration_required`, `oauth_https_required` and the other OAuth codes of [Remote MCP](../design/security-and-trust.md#remote-mcp-network-policy-and-oauth), `elicitation_forbidden` (403) and `elicitation_gone` (404). No response ever contains a secret value.
- **ConnectorView:** `{id, scope:"org"|"personal", name, label, transport:"http"|"sse"|"stdio", url?, command?, args?, cwd?, auth:"none"|"headers"|"oauth", credential_mode:"shared"|"per_user", enabled, status:"connected"|"needs_auth"|"needs_secrets"|"error"|"idle"|"pending_confirmation", last_error?, secrets_set:{key:bool}, header_keys:[name], env_keys:[name], disabled_tools:[name], timeout_s, groups? (org), tool_count?, source:"manual"|"ai"|"import:<format>"|"legacy", manageable, oauth_warning?:"https_required"}`. `secrets_set` reports the viewer's own credentials: empty for a shared organization connector in a user's view; the shared credentials in the administrator's. `status` is `pending_confirmation` for a connector the AI added or imported (or a workspace file import) until its owner confirms it: it is not offered to runs, never connected, and takes no credentials, sign-in or test (409 `confirmation_required`). `status` is `needs_secrets` while a declared key has no value, `needs_auth` while OAuth has no token, `connected` while a live connection exists. `oauth_warning` appears when `public_base_url` is neither https nor loopback.
- **Connector body** (POST/PATCH): `{name, label?, transport:"http"|"sse"|"stdio", url?, command?, args?, cwd?, auth?, env?, headers?, header_keys?, env_keys?, timeout_s?, enabled?}`. `http` is Streamable HTTP with SDK `auto` negotiation, `sse` the legacy transport. `env` (stdio) and `headers` (remote) map names to values: a non-empty value is stored as a secret, an empty string declares the key as missing. PATCH takes the same fields except `name`, plus `disabled_tools:[name]` and `secrets:{KEY:value|null}` (routed to the list the key is declared in; `null` deletes); `header_keys`/`env_keys` replace the lists. Changing `url` deletes OAuth tokens. Stdio is personal only, needs `private_agent`, and forces `auth:"none"`.
- **Personal** (mutations need `install_extensions`): GET `/api/mcp/connectors?scope=private|chat|chat-<id>|channel-<id>` → `{connectors:[ConnectorView], can_install, oauth_warning?}` (the user's group-assigned enabled organization connectors and, with `install_extensions`, their own; chat lists remote ones only; channel lists the channel's enabled ones). POST `/api/mcp/connectors` → `{connector}` (201). PATCH/DELETE `/api/mcp/connectors/{id}`. POST `…/{id}/connect` → `{authorize_url}` (OAuth; per-user organization connectors and personal ones). POST `…/{id}/confirm` → `{connector}` (owner only; confirms where the connector connects and enables it). DELETE `…/{id}/connection` disconnects (deletes the caller's tokens). POST `…/{id}/test` → `{ok, server:{name,version}|null, tools:n, error?}` (never an HTTP error). GET `…/{id}/catalog` → `{tools:[{name,description,read_only,enabled}], prompts, resources}`. PUT `…/{id}/credentials` `{secrets:{KEY:value|null}}` → `{connector}` for the caller's own personal connector or the caller's own secrets of a per-user organization connector (shared organization credentials are administrator-only). Another user's personal connector is 404.
- **Import:** GET `/api/mcp/import/detected` (`private_agent`) → `{files:[{path,format,servers:[name]}]}`, a scan of the personal workspace; it creates nothing. POST `/api/mcp/import` `{path}` (a `/workspace/...` file) or `{text}` (config text or `claude mcp add`/`codex mcp add` lines) → `{connectors:[ConnectorView], missing:[{connector, kind:"oauth"|"secrets", keys?}], skipped:[{name, reason:"exists"|"local_not_allowed"}]}`; pasted `text` is the user's own and starts confirmed, a workspace `path` starts `pending_confirmation`. All servers are validated before any is created (`import_invalid`). Formats: `claude`, `claude-desktop`, `cursor`, `vscode`, `opencode`, `codex`, `claude-cli`, `codex-cli` (stored as `source:"import:<format>"`). Literal secrets are stored; `${VAR}` placeholders become empty declared keys listed in `missing`. 
- **Prompts:** GET `/api/mcp/prompts?scope=` → `{prompts:[{connector, connector_label, name, title, description, arguments:[{name,description,required}]}], connectors:[{name,label}]}` (`connectors` = every available connector of the scope). POST `/api/mcp/prompts/render` `{scope?, connector, name, arguments:{name:string}}` → `{text}` (messages flattened for the composer; assistant messages are prefixed `Assistant: `).
- **Elicitation:** POST `/api/mcp/elicitations/{id}` `{action:"accept"|"decline"|"cancel", content?}` → `{ok:true}`. Only the user who triggered the run may answer (403 `elicitation_forbidden`); an expired or answered id is 404 `elicitation_gone`; an `accept` of a form must satisfy its schema (400 `elicitation_invalid`). Pending elicitations are in memory (10-minute timeout = cancel).
- **Administrator** (`system_settings`): GET `/api/admin/mcp/connectors` → `{connectors:[ConnectorView+{groups, oauth:{scopes,client_id|null,client_secret_set}}], groups:[names], oauth_redirect_uri, oauth_warning?}`; POST (`name`, `transport:"http"|"sse"`, `credential_mode:"shared"|"per_user"` default `shared`, `groups` default `["*"]`, `oauth_client:{client_id,client_secret?}|null`, `oauth_scopes?`, plus the connector body; with `shared` credentials `headers` values are stored as the shared secrets) and PATCH/DELETE `/api/admin/mcp/connectors/{id}` (`oauth_client` omitted keeps it, `null` clears it; `secrets` only for `shared`); POST `…/{id}/connect` (shared OAuth), DELETE `…/{id}/connection`, POST `…/{id}/test`, GET `…/{id}/catalog` (as the shared owner); GET `/api/admin/mcp/calls?connector=&limit=` → `{calls:[{id,at,user_id,username,display_name,scope_key,connector_id,connector_name,connector_label,tool,status,duration_ms}]}`; GET/PUT `/api/admin/mcp/settings` `{private_networks:[CIDR|host]}` (400 names the bad entry). A personal connector cannot take the name of an organization connector.
- **Channels** (`manage_channels`): GET `/api/channels/{id}/mcp` → `{connectors:[ConnectorView], connector_ids:[id]}` (eligible: shared-credential remote organization connectors); PUT `{connector_ids}` → the same shape; ids of ineligible connectors are dropped, not stored. Eligible: enabled-for-use organization connectors with shared credentials, a remote server and groups `["*"]` (a group-restricted connector can never reach a channel). The view a channel manager gets is reduced: `{id, scope, name, label, transport, auth, enabled, status, origin}` (the URL origin only; no groups, OAuth client, secret state or error detail).
- **OAuth:** POST `/connect` returns `{authorize_url}`; GET `/api/mcp/oauth/callback?code&state` completes the exchange (state-bound, 10-minute, single use) and returns a static page that posts `{type:"mcp-connected", connector}` to `window.opener`; GET `/api/mcp/oauth/client.json` serves the client metadata document (only when `public_base_url` is https).
- **SSE events** (durable, on the conversation scope): `mcp_action_required {connector:{id,name,label,scope,transport,destination,source:"ai"|"import"|"manual",state:"pending_confirmation"|"active",url?(origin)|command+args}, kind:"oauth"|"secrets"|"confirm", keys?}` (`destination` is the URL origin or the command line the connector would contact or run, shown so the user can confirm it before entering secrets; `confirm` = nothing else is needed yet); `mcp_elicitation {id, user_id, connector:{id,name,label}, mode:"form"|"url", message, schema?, url?, expires_at}` and `mcp_elicitation_resolved {id, action, reason?:"timeout"|"cancelled"}`.
- **Gateway:** POST `/internal/agent/tools/mcp` `{action,arguments,context}` returns `{content,data,is_error}` (typed failures are tool errors with `data.code`). `call {name}` (`mcp__<connector>__<tool>`) or `{connector,tool}` with `arguments`, `describe`, `list`, `list_resources {connector}` and `read_resource {connector,uri}` serve every scope; `data.images:[{mimeType,data}]` carries at most 4 images. `add {name,label?,transport,url|command+args+cwd,auth,env_keys?,header_keys?}` (rejects `env`/`headers` values), `remove {name}`, `import {path|text}`, `connect {name}`, `enable {name}`, `disable {name}` serve personal root runs only and need the user's `install_extensions`. Availability is recomputed server-side on every call; subagents (identified by their child run) are filtered by type. `call` may last up to 15 minutes (elicitation waits), other actions 60 s; abandoning the request cancels the server-side call.
- **Run payload:** the run request gains `mcp: {tools:[{name,connector,tool,description,input_schema,read_only}], deferred, catalog_text?}` and `"mcp"` in `tools` whenever the scope has an available connector (and always for the personal root). Subagent runs also list the filtered `mcp__*` names. See [integrations](../design/integrations.md#mcp) for names, deferral and filtering.

## Background tasks
Personal AI only; the caller must be the owner with `private_agent`. Another user's task is 404. A task is a subagent or a Manager-supervised background process, shown as `bg-<n>` (`n` = `background_tasks.id`).
- TaskView: `{id:"bg-<n>",kind:"process"|"agent",name,label,agent_type:"scout"|"task"|null,status:"running"|"completed"|"failed"|"stopped"|"interrupted",reason,exit_code,started_at,ended_at,result_preview,created_by_message_id,created_by_tool_call_id,current,usage}`. `label` is the command (processes, at most 500 characters) or the task's first line. `result_preview` is at most 2000 characters (the report of an agent; the output tail of a process). `current` is `{tool,summary}` of the latest unfinished tool of a running agent, otherwise null. `usage` is `{total_tokens}` once an agent has finished, otherwise null.
- GET `/api/tasks` → `{tasks:[TaskView]}`: running first, then newest; at most 100.
- GET `/api/tasks/{id}` → `{task}`; agents add `work` (the bounded work trace, same object as `metadata.work`) and the full `result`; processes add the stored output tail as `result`.
- GET `/api/tasks/{id}/output?offset=&wait_ms=` → processes only (400 for agents): Manager's `{data,offset_start,next_offset,retained_from,eof}`; `offset` -1 (default) is the tail and `wait_ms` (at most 30000) long-polls.
- POST `/api/tasks/{id}/stop` `{}` → `{task}`. Stopping a finished task returns it unchanged. A process is killed through Manager with an audit receipt and is `stopped` only once Manager reports it; an unconfirmed kill returns 409 and leaves the task `running`. An agent's run is cancelled and the task becomes `stopped` with reason `user`.
- Status: a process becomes `completed` on exit code 0, `failed` on a non-zero exit, `start_failed` or timeout, `stopped` when killed by a user, run cancellation or sandbox stop request, and `interrupted` when Manager restarted (reason `system_restart`) or its sandbox stopped (`sandbox_stopped`). An agent becomes `completed`, `failed` (the run failed), `stopped`, or `interrupted` (reason `platform_restart` or `stream_lost`; never replayed).
- SSE (the personal scope's events stream): `task {task:TaskView}` on every status change and, while an agent runs, throttled to at most 2 per second for its current activity.
- Task notice: when a task finishes undelivered, Platform inserts a `system` message `metadata {kind:"task_notice",task_ids:["bg-<n>"],tasks:[TaskView],status}` and a durable queued job `{notice:true,task_ids}` in the personal scope. A notice still queued absorbs further finished tasks (ids and views appended). When the worker starts it, tasks delivered meanwhile (by `wait`) are dropped; with none left the job settles without a run and the message gets `skipped:true`. Otherwise Platform sets `delivered_at` and runs a turn whose prompt is an escaped `<background-task-results>` block (per task: id, kind, name, status, exit code, duration and the result or output tail, each result at most 4000 characters) followed by "Continue the user's work using these results."; the reply is an ordinary assistant message with `reply_to` the notice. Notices behave like schedule occurrences: user messages queue behind them and are never inserted into them.
- Gateway: POST `/internal/agent/tools/tasks` `{action,arguments,context}` (same bearer and context as `web|browser|schedule`, root personal scope only; subagent sessions are refused with 403) → `{content,data,is_error}`. Business failures (limits, unknown or foreign id, nothing to wait for) are `is_error:true` with HTTP 200. Actions: `spawn {agent?:"scout"|"task",tasks:[{name?,task}],context?}` (1–8 tasks; limit 8 running subagents per user) → `data.tasks:[{id,name,agent_type}]` at once; `register_process {process_id,delivered,name?,command}` (idempotent; reads the current Manager view, so a process that already ended is captured; `delivered:true` suppresses any notice) → `data.task_id`; `list`; `status {id}`; `output {id,offset?}` (process: Manager read; agent: its report so far); `input {id,text?,eof?}` and `stop {id}` (processes through Manager with audit receipts; `stop` also stops agents); `wait {ids?,timeout?}` (seconds, at most 1800).
- `wait` returns the first terminal, undelivered task of the owner (restricted to `ids` if given), oldest end first, and sets `delivered_at`, so it is delivered once. It returns early with a note and no task when a user message is pending insertion into the current run, returns a timeout note after `timeout`, and fails when nothing is running and nothing is undelivered. A cancelled run or closed connection never consumes a delivery.
- Limits: 8 running subagents per user (Platform) and 16 running background processes per user (enforced by Manager at start). Running subagents count in the update readiness field `active_agent_tasks`; background processes do not.
- Processes: Platform follows Manager's `process/changes` feed from the cursor in `settings.process_changes_cursor` using its executor credential, and also reconciles running registered processes against Manager's list at startup.

## Schedules
- Schedules have no user API. They are managed only by the personal AI's `schedule` tool through the internal gateway `POST /internal/agent/tools/schedule`.

## Admin and model settings
- GET `/api/admin/users` → `{users:[]}`; POST same `{username,password,display_name?,role?,permission_group?,model_policy?,timezone?}` → `{user}`; PATCH `/api/admin/users/{id}` same mutable user fields plus `{password?,active?}` → `{user}`; DELETE same → `{ok:true}` (deactivate/revoke). Admin user objects (also the impersonation response) add `model_policy` (the name of the account's model policy group; default `default`, must name an existing group) to the self-facing user shape. `model_name`, `chat_model_name` and `thinking_depth` no longer exist.
- POST `/api/admin/users/{id}/impersonate` with `{}` → `{user}` for the target, and sets a fresh normal session cookie for that account (same attributes as login), replacing the admin's cookie. Admin only and same-origin; 404 if the target is missing or deactivated, 400 if it is the caller. The target's `token_version` and other sessions are untouched.
- GET `/api/admin/permission-groups` → `{groups:[{name,permissions:[string]}]}`; PUT same `{groups:[...]}` → same.
- GET `/api/admin/model-policies` → `{policies:[{name,label,slots:{personal,channel,chat,scout,worker}}],members:{name:count}}` (`members` counts every account, active or not); PUT `{policies:[...]}` replaces the whole list and returns the same shape. The list must be nonempty; `name` matches `[a-z][a-z0-9_-]{0,63}` and is unique; `label` is 1–64 characters; every slot is required and is `{model,thinking}` with `model` a string of at most 128 characters (`""` = system default, the first catalog model) and `thinking` one of `off|minimal|low|medium|high|xhigh`. A group still referenced by any user cannot be removed (409). Stored in settings key `model_policies_v1`.
- GET/PATCH `/api/admin/branding` → `{branding}`; patch accepts branding fields.
- GET `/api/admin/models` → `{models:[{id,name,contextWindow?,maxTokens?}],connected:boolean}`. Positive token limits are included when advertised by the provider and forwarded to Runtime; visible authorized Codex model IDs are not limited to a bundled static list.
- POST `/api/admin/oauth/start` `{}` → `{flow_id,provider,kind,status,complete,expires_at,verification_url,user_code,poll_interval}`; POST `/api/admin/oauth/{flow_id}/poll` `{}` → same, status `waiting_for_user` or `complete`. DELETE `/api/admin/oauth` → `{ok:true}`.
- GET `/api/admin/usage` → `{input_tokens,output_tokens,cache_read_tokens,cache_write_tokens,total_tokens,cache_hit_ratio,events:[]}` (ratio cache_read/(input+cache_read), zero when denominator zero).
- GET `/api/admin/system` → Manager `/v1/status` JSON unchanged; GET/PATCH `/api/admin/system/config` → Manager config unchanged; POST `/api/admin/system/check` `{idempotency_key}` → Manager check unchanged; POST `/api/admin/system/operations` `{operation,idempotency_key,expected_generation?}` → Manager operation unchanged.
- Roles and permission groups are independent. Editable permission catalog: `read_workspace`, `chat`, `private_agent`, `manage_channels`, `manage_users`, `system_settings`, `install_extensions` (labels en "Install skills and connectors", zh-CN "安装技能和连接器", zh-TW "安裝技能和連接器"). Existing group names may be retained or new groups added; a referenced group cannot be removed.
- Model policy groups (策略组) are the only place a model or thinking depth is chosen, and only administrators edit them. Each account belongs to exactly one group. The slot that applies is chosen server-side by usage: `personal` (personal AI turns, schedules, background-task notice turns), `channel` (the channel main agent, using the triggering user's group), `chat` (standard chat), `scout` (`scout` subagents), `worker` (`task` subagents). Manual compaction uses the slot of the scope being compacted. A message inserted into a running turn keeps that run's model. An empty slot model resolves to the first catalog model.
- Branding `logo` accepts a PNG/WebP data URL (maximum 256 KiB and 4096 pixels per dimension); null clears it.
- OAuth `expires_at` is epoch seconds, not an ISO date. Expired device flows return HTTP 410.
- Usage totals are all-time; `events` contains the newest 200 events without date filters. Events contain id/user_id/username/display_name/scope_type/scope_id/scope_name/request_message_id/response_message_id/provider/model/input_tokens/output_tokens/total_tokens/degraded/created_at and parsed `raw_usage` (including cache counters).
New events add `raw_usage.kind:"agent"|"chat"|"compaction"`; missing kind on old rows means agent. `scope_name` holds the channel name or chat conversation title, and is empty for personal AI. Chat keeps legacy `scope_type:"private"` but uses its conversation UUID as `scope_id`. Completed manual compaction records the Runtime-reported input/output/cache usage and model with null request/response message IDs; its tokens contribute to totals and cache-hit ratio. `nothing_to_compact` creates no token-usage event.

## Internal contracts
Manager bearer routes and health remain byte-compatible; healthz `{status:"ok",service:"agent-platform"}`. POST `/internal/manager/update/{readiness|commit-release|abort-release}` body `{operation_id}`; readiness `{reserved,active_agent_tasks,queued_agent_jobs,running_agent_jobs,admissions_in_progress,blocker_error}`; release `{released:true}`. GET `/internal/manager/health` includes status, schema_version, update_reserved and readiness counters.
Readiness blockers: `active_agent_tasks` is Platform's in-memory active work (queue tasks and unsettled runs) plus the number of running subagent tasks (`background_tasks` rows with `kind='agent'` and `status='running'`); queued notice jobs count in `queued_agent_jobs`. Running background processes never block an update.
Internal health additionally includes `reserved:false`; `update_reserved` reports actual reservation ownership. Abort with any nonempty operation id is idempotently successful when unreserved. Commit replays only the most recently committed id while unreserved; a competing owner returns 409. A failed commit keeps admission frozen.
Installed container startup requires successful Manager reservation recovery before starting workers or schedules. An absent or unreachable control socket fails startup; it never disables the Manager boundary.
Runtime bearer POST `/api/agent/tools/credentials/resolve` `{provider,model,scope_key?,force_refresh?}` → `{provider,access_token,token_type:"Bearer",expires_at,base_url,model}`. POST `/internal/agent/tools/{web|browser|schedule|skills|artifacts|mcp}` `{action,arguments,context:{sid,scope_key,run_id,owner_user_id?,channel_id?}}` → `{content,data,is_error}`; `skills` is specified under [Skills](#skills) and `artifacts` under [Artifacts](#artifacts).
POST `/internal/agent/tools/tasks` (subagents and background tasks, personal root scope only) is specified under [Background tasks](#background-tasks). The executor credential (`AGENT_PLATFORM_MANAGER_EXECUTOR_TOKEN_FILE`) lets Platform call Manager's `process/*` executor routes over the same Unix socket; it is a separate secret from the control credential.

## Migration
`enterprise-agent-platform migrate` creates the live tables if missing and then applies an ordered list of forward migrations recorded in `schema_migrations`. A migration is a list of SQL statements or a Python callable that receives the open connection. Each version is applied once, in the same transaction and file lock as the schema statements; the highest recorded version is the `schema_version` that health and the release contract report. Migration `2026100101` (`drop-pre-pi-rollback-compat`) drops the tables, triggers and full-text indexes of removed features, deletes `durable_jobs` rows whose kind is not `agent`, and removes the obsolete `durable_agent_jobs_start_message_id` setting and the `pi_schema_migrations` ledger. No pre-Pi data is retained. Migration `2026100201` (`chat-model-follows-personal-ai`) adds `users.chat_model_name` (default `""`), copies each non-empty `chat_model_policies.default_model_id` into it, then drops `chat_model_policies` and `chat_conversations.model_id`; per-user allowed-model lists are discarded.
Migration `2026101101` (`background-tasks`) creates `background_tasks` (see [data model](../design/data-memory-sessions.md#product-database)) and its indexes with `CREATE ... IF NOT EXISTS` and adds no data.
Migration `2026101201` (`model-policy-groups`) writes settings `model_policies_v1` with one group, `default` (label `默认`), seeded from the lowest-id active administrator (else the lowest-id account; with no accounts every model is `""` and every thinking depth `medium`): `personal`, `channel` and `worker` take that account's `model_name` and `thinking_depth` (legacy `none` becomes `off`); `chat` and `scout` take its `chat_model_name`, or `model_name` when empty, with the same depth. Every user gets `model_policy='default'`, then `users.model_name`, `users.chat_model_name` and `users.thinking_depth` are dropped (no compatibility columns). A fresh install seeds the same group with every model `""` and depth `medium`. The migration is forward-only and raises the release contract's `database_schema_version` to 2026101201.
Migration `2026101301` (`skills`) creates `skills` and `skill_preferences` (see [data model](../design/data-memory-sessions.md#product-database)) with `CREATE ... IF NOT EXISTS`, and appends `install_extensions` to every stored permission group that is named `admin`, `manager` or `member` or contains `private_agent` or `chat`, and renames `<data_dir>/workspaces/**/.agent-platform/skills/<n>-<8 hex>` directories to `<n>` when the SKILL.md name normalizes to `<n>` and `<n>` is free (never following symlinks; it runs before any sandbox starts so the first catalog is stable) (when `permission_groups_v1` is absent the defaults already include it for `admin`, `manager` and `member`). It is idempotent: a group that already has the permission is unchanged. Existing workspace skills get no row and are shown with source `workspace`.
Migration `2026101401` (`artifacts`) creates `artifacts` and `artifact_versions` (see [data model](../design/data-memory-sessions.md#product-database)) with `CREATE ... IF NOT EXISTS` and adds no data. It is idempotent: the blob store `<data_dir>/artifacts/blobs/` is created on first publish.
Migration `2026101501` (`mcp`) creates `mcp_connectors`, `mcp_secrets`, `mcp_channel_connectors`, `mcp_calls` and `mcp_catalog_cache` (see [data model](../design/data-memory-sessions.md#product-database)) with `CREATE ... IF NOT EXISTS`, then imports each `<data_dir>/workspaces/user-<id>/.agent-platform/mcp.json` (read through pinned descriptors, never through symlinks, at most 256 KiB) as personal stdio connectors named after the slugified server id with source `legacy`: env keys are declared and their literal values move into `mcp_secrets`, invalid files and servers are skipped, an existing name for that user is skipped, and the files are left untouched. It is idempotent, raises the release contract's `database_schema_version` to 2026101501, and adds no setting.

New personal/channel scopes record their workspace, sandbox and lifecycle identity in `agent_scopes`. Workspace `AGENTS.md` and `.agent-platform/skills` are read as they are on disk (never through symlinks).
